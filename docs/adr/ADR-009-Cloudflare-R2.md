# ADR-009 — Adopt Cloudflare R2 as the Primary Object Storage

**Status:** Accepted

**Date:** 2026-08-07

**Decision ID:** ADR-009

**Owners:** Engineering

---

# Context

Project Loom requires a scalable object storage system for:

- Product images
- Product videos (future)
- Seller logos
- Store banners
- Customer review images
- Return evidence photos
- Generated reports
- Export files
- Marketing assets

The storage solution must provide:

- High durability
- Global delivery
- Low operational overhead
- Cost-effective scaling
- S3-compatible APIs

Candidate solutions evaluated:

- Cloudflare R2
- AWS S3
- Google Cloud Storage
- Azure Blob Storage
- MinIO (self-hosted)

---

# Decision

Project Loom will adopt **Cloudflare R2** as the primary object storage service.

Cloudflare R2 stores all binary assets.

PostgreSQL stores only metadata and references.

---

# Responsibilities

Cloudflare R2 stores:

- Product images
- Seller branding assets
- Customer uploads
- Export files
- Reports
- Static assets generated by the application

---

# Responsibilities Excluded

Cloudflare R2 does **not** store:

- Business records
- User profiles
- Orders
- Payments
- Analytics
- Search indexes

Only file metadata is stored in PostgreSQL.

---

# Why Cloudflare R2?

Advantages:

- S3-compatible API
- Zero egress fees
- Global infrastructure
- Excellent integration with Cloudflare CDN
- Competitive pricing
- Easy migration path

---

# Why Not AWS S3?

S3 is an excellent service.

Reasons for selecting R2 instead:

- No egress charges
- Better alignment with Cloudflare CDN
- Lower expected operational costs for image-heavy workloads

Migration to S3 remains possible because R2 is S3-compatible.

---

# Why Not MinIO?

Reasons:

- Self-hosting operational burden
- Scaling complexity
- Backup responsibility
- Infrastructure maintenance

Managed object storage better fits the project's operational goals.

---

# Upload Flow

```text id="uploadflow"
Client

↓

Request Upload

↓

API Generates Signed URL

↓

Client Uploads Directly to R2

↓

API Stores Metadata

↓

Asset Available
```

The application server should avoid proxying large uploads whenever possible.

---

# Metadata

PostgreSQL stores:

- Asset ID
- Owner
- MIME type
- File size
- Width
- Height
- Storage key
- Public URL (if applicable)
- Created timestamp

Binary content is never stored in PostgreSQL.

---

# Image Processing

Workflow:

```text id="imageprocessing"
Upload

↓

BullMQ

↓

Image Worker

↓

Sharp

↓

Generate Variants

↓

Store in R2
```

Generated variants may include:

- Thumbnail
- Small
- Medium
- Large
- Original

---

# CDN Strategy

Assets are delivered through Cloudflare CDN.

Benefits:

- Reduced latency
- Global caching
- Lower origin load
- Improved user experience

---

# Security

Requirements:

- Signed upload URLs
- Least-privilege API credentials
- Private buckets by default
- Public access only where required
- MIME type validation
- File size validation

Uploads must be scanned and validated before being trusted by the application.

---

# File Naming

Object keys use UUIDs.

Example:

```text id="objectkeys"
products/

stores/

reviews/

returns/

reports/
```

Human-readable filenames are stored only as metadata.

---

# Lifecycle Management

Retention policies:

Temporary uploads:

- Automatic expiration

Reports:

- Configurable retention

Product assets:

- Permanent unless removed

Unused assets should be cleaned periodically.

---

# Monitoring

Track:

- Storage usage
- Upload failures
- Download latency
- CDN cache hit ratio
- Processing failures

---

# Scaling Strategy

Cloudflare R2 scales automatically.

Application scaling should focus on:

- Upload workers
- Image processing
- Metadata persistence

---

# Risks

Potential risks:

- Large uploads
- Invalid files
- Orphaned objects
- CDN cache inconsistencies

Mitigations:

- Signed uploads
- Validation
- Periodic cleanup jobs
- Monitoring
- Asset reconciliation processes

---

# Consequences

Positive:

- Low-cost storage
- Global delivery
- Excellent scalability
- Reduced application server load

Negative:

- Additional infrastructure dependency
- Eventual consistency for newly processed image variants
- Operational processes required for lifecycle management

---

# Success Criteria

This decision remains valid while:

- Upload performance remains acceptable.
- Storage costs remain predictable.
- Asset delivery meets performance targets.
- Binary data remains decoupled from transactional storage.
