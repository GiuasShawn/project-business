# Document 08.1 — Database Philosophy & Standards

**Project:** Project Loom *(Working Name)*  
**Document ID:** DB-08.1  
**Version:** 1.0.0  
**Status:** Living Specification

---

# 1. Purpose

This document establishes the database philosophy, modeling standards, and conventions for Project Loom.

Every PostgreSQL table, index, migration, relationship, and query must conform to this specification.

---

# 2. Goals

The database shall be designed for:

- Performance
- Consistency
- Scalability
- Auditability
- Maintainability
- Extensibility

---

# 3. Source of Truth

Each business entity has exactly one source of truth.

Examples:

| Entity | Owner |
|---------|-------|
| Users | Users Domain |
| Stores | Stores Domain |
| Products | Products Domain |
| Inventory | Inventory Domain |
| Orders | Orders Domain |
| Payments | Payments Domain |
| Returns | Returns Domain |
| Analytics | Analytics Domain |

Duplicate ownership is prohibited.

---

# 4. Database Engine

- PostgreSQL
- UTF-8 encoding
- UTC timestamps
- ACID transactions

---

# 5. ID Strategy

All primary keys use:

- UUID v7 (preferred)
- UUID v4 (fallback)

Sequential integer IDs are prohibited.

IDs are immutable.

---

# 6. Table Naming

Rules:

- snake_case
- plural nouns
- descriptive names

Examples:

```text
users
stores
products
orders
order_items
seller_products
inventory_transactions
```

Avoid abbreviations unless universally understood.

---

# 7. Column Naming

Rules:

- snake_case
- descriptive
- singular

Examples:

```text
user_id
store_id
product_id
created_at
updated_at
deleted_at
status
```

---

# 8. Common Columns

Every business table includes:

```text
id
created_at
updated_at
```

Where applicable:

```text
deleted_at
created_by
updated_by
deleted_by
version
```

---

# 9. Timestamp Rules

All timestamps:

- UTC
- timestamptz
- generated by the server

Never trust client timestamps.

---

# 10. Foreign Keys

Every relationship shall enforce referential integrity.

Foreign keys:

- NOT NULL unless optional
- indexed automatically when required
- named consistently

Example:

```text
store_id

REFERENCES stores(id)
```

---

# 11. Unique Constraints

Used for:

- emails
- usernames
- store subdomains
- SKUs
- coupon codes
- transaction references

Business uniqueness must be enforced at the database level whenever possible.

---

# 12. Check Constraints

Examples:

Price ≥ 0

Stock ≥ 0

Commission ≥ 0

Rating BETWEEN 1 AND 5

Percent BETWEEN 0 AND 100

Business rules should be enforced in both the application and database where practical.

---

# 13. Relationships

Relationship types:

- One-to-One
- One-to-Many
- Many-to-Many

Join tables shall be explicit.

Example:

```text
seller_products

seller_id

product_id
```

Never store comma-separated IDs or JSON arrays for relational data.

---

# 14. JSON Usage

Use JSONB only for:

- flexible metadata
- third-party payloads
- configuration
- feature flags

Never use JSONB to replace normalized relational structures.

---

# 15. Soft Deletes

Allowed only when:

- business history matters
- legal retention requires it
- audit history is required

Otherwise:

Hard delete.

---

# 16. Audit Strategy

Critical business entities must be auditable.

Audit includes:

- who changed it
- when
- previous value (where required)
- new value
- reason (optional)

Audit logs are immutable.

---

# 17. Transactions

Required for:

- Checkout
- Order creation
- Payment capture
- Refunds
- Inventory reservation
- Payout creation

No partial financial updates.

---

# 18. Optimistic Locking

Tables with concurrent updates should include:

```text
version
```

to prevent lost updates.

---

# 19. Indexing Strategy

Indexes shall exist for:

Primary Keys

Foreign Keys

Emails

Subdomains

SKUs

Status

Created At

Frequently filtered columns

Composite indexes shall be created based on measured query patterns.

---

# 20. Full Text Search

Relational search remains in PostgreSQL where appropriate.

Customer-facing search is handled by Meilisearch.

The database is not the primary search engine.

---

# 21. Caching Philosophy

Redis caches:

- product pages
- categories
- collections
- analytics summaries

Never cache:

- inventory mutations
- payment status
- authentication decisions

---

# 22. Partitioning

Reserved for future growth.

Potential candidates:

- audit_logs
- analytics_events
- notifications
- orders (time-based)

Partitioning should only be introduced after observing production workloads.

---

# 23. Migration Strategy

Schema changes:

- forward-only
- version controlled
- peer reviewed
- reversible where practical

Manual production edits are prohibited.

---

# 24. Data Retention

Examples:

Audit Logs → Permanent

Orders → Permanent

Payments → Permanent

Notifications → Configurable

Analytics Events → Configurable

Sessions → Expire automatically

---

# 25. Performance Targets

Single-row lookup:

<10 ms

Indexed queries:

<50 ms

Complex business queries:

<200 ms

Large reports:

Run asynchronously where possible.

---

# 26. Security

Sensitive data:

- encrypted at rest where appropriate
- never logged
- access controlled
- least privilege

Passwords:

Never stored.

Only password hashes.

---

# 27. Acceptance Criteria

Database design is compliant when:

- every table follows naming standards
- every relationship is normalized
- every financial entity is auditable
- every migration is versioned
- every critical query is indexed appropriately
